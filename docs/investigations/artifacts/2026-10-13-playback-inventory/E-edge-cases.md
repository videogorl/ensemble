## 6. Open questions

- **Q1. What does system Now Playing publish during a skip load?** INV-0906 says loading and buffering publish rate 0 and the bridge never forces a playing state. `933ea364` and `58719d24` (two weeks earlier) made the bridge publish "playing" through a skip load to stop the controls disappearing, and the test added then (`testSkipTransitionKeepsSystemNowPlayingActiveWhileLoading`) no longer exists. The current rule needs reading from source before C79 and C127 can both be rows.
- **Q2. Is the stale-callback rule one rule or two?** Dropping an event from an old SessionID covers most cases, but the Apple adapter also has to act on a stale completion (re-assert the latest stop or pause on the shared player, C83). Should that be an effect the reducer emits on a dropped event, or adapter-internal?
- **Q3. Where do MusicKit's inferred events live?** Previous inference (C87) and final-entry reset (C86) need playhead history. Proposed here as adapter-internal, emitting plain `previous` and `ended`. If the reducer should own them, `PlaybackPosition` needs the last playing time and a "restart observed" marker.
- **Q4. Availability as reducer input.** C19 and C20 need per-item availability (downloaded, server known-offline, device offline, cellular allowed). Is that part of `PlaybackState`, delivered as `system` events, or passed with each command?
- **Q5. Timers.** Settle window (C103), rebuffer timeout (C116), stuck-loading watchdog (C35), end-confirmation delay (C85), transition lease (C77), prefetch cooldown (C115). Which are reducer-visible (effect "start timer" plus event "timer fired") and which stay inside engines and handlers? PLAN 4.3 says "no clocks" in reducer tests.
- **Q6. Is the watchdog still live?** The comments at `PlaybackService.swift:5898-5907` still describe AVPlayer. Confirm whether C35 is current behaviour or dead code.
- **Q7. Are C117 and C118 still current?** They come from the archived inventory (downloaded-alternative scan, auto-resume after a successful health check). Confirm against source.
- **Q8. Failure counting scope** (see G11): per track or per consecutive attempt across tracks, and does an automatic skip happen before the limit?
- **Q9. Shuffle randomness.** A pure reducer needs the random source injected or the shuffled order supplied by the event. Which?
- **Q10. Queue-replacement confirmation** (C10): does the reducer return a "needs confirmation" effect and wait for a second command, or does the UI ask the snapshot first? Today the view model decides.
- **Q11. Repeat One on Apple items** (C60): the mirror to MusicKit is an effect on every repeat-mode change and on every Apple start. Is a natural `ended` ever expected from an Apple item under Repeat One, and what should the reducer do if one arrives?
- **Q12. `PlaybackRoute` contents.** The acceptance list has one interruption item, but the handoff tables carry pause reason (user, interruption, disconnect, system), settle window and skip gating. Is pause reason part of `session` or `route`?
- **Q13. iOS floor versus Apple Music floor.** The app floor is now iOS 17, mixed queues need 18 (POL-PQ). Is the iOS 17 Plex-only path still required in the reducer, or only in source enablement?
- **Q14. Commit bodies.** Of the 150 commits read, almost none has a message body, so the root causes in B41 to B67 marked "diff" are my reading of the change, not a written record. They should be confirmed by whoever writes the corresponding table rows.
