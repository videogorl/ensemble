# Plex smart-playlist count freshness

Read-only endpoint investigation on 2026-10-05, following
[issue #98](https://github.com/videogorl/ensemble/issues/98). The affected server
reported PMS `1.43.4.10903-e5521bd8c`. No production code or saved playlist rules,
membership, ratings, or library settings changed. All server requests used GET.
Plex recomputed derived playlist statistics during those reads, as its API
documents. Raw responses, credentials, server/library identities, and private
probe scripts remain outside Git under `/tmp/ensemble-plex-count.TYwmhc`.

## Result

The mismatch was stale list-level smart-playlist statistics, not pagination or
tracks from other libraries being omitted from the count. Two smart playlists
initially shared the same incorrect list count. After reading their individual
metadata and contents, the next inventory returned their current counts:

| Response | Playlist A | Playlist B |
| --- | ---: | ---: |
| Initial `/playlists` leafCount | 1,595 | 1,595 |
| Individual `/playlists/{id}` leafCount | 3,460 | 291 |
| Complete `/playlists/{id}/items` entries | 3,460 | 291 |
| Direct saved-filter results | 3,460 | 291 |
| Subsequent `/playlists` leafCount | 3,460 | 291 |

The direct saved filters returned exactly the same rating keys in the same order
as each playlist body. Both filters explicitly selected tracks (`type=10`) within
one music library. Every returned playlist track had that library's section ID.
The server had four music libraries; separate track-total queries returned 3,460,
1,451, 439, and 56. The affected body was the 3,460-track library, not a combination
of libraries or an artist/album count expanded into tracks.

For Playlist A, the unpaged body declared size and leafCount 3,460 and contained
3,460 distinct rating keys. Explicit 100-item pages at offsets 0 and 3,360 declared
totalSize 3,460 and matched the corresponding first/last slices of the complete
body. The 1,595 value was not a page size or offset. There were 3,418 distinct
recording GUIDs, so recording-level deduplication also does not explain 1,595.
Playlist B had 291 distinct rating keys and GUIDs.

Both playlists' duration and updatedAt changed between the initial and subsequent
inventories. The evidence establishes stale initial statistics and their refresh
during this sequence. It does not establish why the original statistics had aged,
or distinguish which individual GET caused persistence of the refreshed values.
There was no explicit metadata-refresh request or remote edit.

## Research

- The official [Plex Media Server API reference](https://developer.plex.tv/pms/)
  describes smart playlists as media queries and says retrieving a playlist or
  its items refreshes metadata, potentially changing duration and item count.
  It also recommends standard pagination for playlist contents. The observed
  before/after sequence agrees with that documented refresh behavior.
- A [July 2022 smart-playlist count report](https://www.reddit.com/r/plexamp/comments/w7it6w/smart_playlist_showing_wrong_number_of_tracks/)
  reported 110 displayed tracks versus 84 rows. Plex staff explained hidden
  grouping by recording GUID and recomputation of statistics when browsing a
  smart playlist. This is related count/refresh behavior, but its deduplication
  explanation and direction differ from the present result.
- In a [September 2026 playlist/download count report](https://forums.plex.tv/t/issues-after-removing-tracks-from-a-playlist-that-has-been-downloaded/942741),
  Plex staff distinguished playlist entries from distinct library tracks. This
  is a separate count-semantics issue, not evidence that this smart playlist
  combines libraries.
- The [Plex community playlist guide](https://forums.plex.tv/t/howto-create-playlists/146040/1)
  distinguishes standard playlists, which can contain multiple libraries, from
  smart playlists generated by a library-scoped filter. The saved queries and
  returned section IDs here independently establish their single-library scope.
- A [2018 smart-filter mismatch report](https://forums.plex.tv/t/creating-smart-playlist-shows-correct-items-in-filter-view-but-only-partially-applies-filter-on-playlist-view/275563)
  describes filter preview versus saved-playlist differences and a reported fix.
  It is historical evidence of a different server filter problem; the exact
  filter/body equality here rules out that explanation for this case.

No exact public report of this particular 1,595-to-3,460 API discrepancy was
found. Public analogies should not be treated as proof of the local cause.

The collaborative Plex Web session was signed out, and no Plexamp desktop surface
was available. A rendered Plex Web/Plexamp comparison was therefore not obtained;
the result above is direct same-server API evidence. No phone interaction was
required.

## Implication for Ensemble

An older playlist listing's leafCount should not by itself establish that a
complete cached body is corrupt. A focused follow-up should validate a smart
playlist count mismatch against its refreshed individual metadata, then reconcile
the header only after successful validated work. This may avoid an unnecessary
body repair without introducing a new service or schema. Its request ordering,
retry behavior, and unavailable-response handling need a concrete implementation
review before changes.

The earlier measured full-body cost remains valid, but those measurements used
the then-stale inventory count. This read sequence corrected Plex's server-side
statistics, so continued repeated repair on this exact live playlist is no longer
established. The existing failed-body retry fix remains separately valid.
General smart-playlist freshness and successful-body checkpoint policy remain
follow-up design questions. No new timer, cache, schema, count policy, or sync
behavior was implemented in this investigation.
